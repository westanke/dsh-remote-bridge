# 复盘：手机端问答卡片为什么「一直不显示」

> 记录一次**代价很大**的排查。结论是代码从头到尾都是对的，错的是排查方法。
> 写下来是因为其中的错误模式会重复出现。

## 结果先说

`ask_user_question` 的问答卡片（插件 v2.2.2 + App v2.2.23）**第一次真机测试就通过了**。
从内核提问到答案回到内核，整条链路一次跑通，没有改一行卡片代码。

端到端证据（插件审计表原文）：

```
提问到达: hasAgent=true sessionId=session-0e864300-… questions=1 hasWait=false
已推帧 userQuestions/requested: callId=bridge-3af742ae-…
chat.question.answer | callId=bridge-3af742ae-… answers=1 questionIds=["target"]
```

## 那么时间花在哪了

花在**为一个不存在的现象反复编造根因**。前后给出过至少四个「根因」，每一个都能自圆其说，
每一个都是错的：

| # | 我给出的「根因」 | 被什么推翻 |
|---|---|---|
| 1 | 工具调用等 120 秒被执行时限掐断 | 日志里**连 `tool/call` 都没有**，说明不是「执行了被切断」 |
| 2 | 我的编排压根无法派发这个工具调用 | 同上，但结论指向错了方向 —— 我去查了框架而不是自己的工具集 |
| 3 | cordis 的 agent 作用域过滤把监听者滤掉了 | `approval/request` 用**完全相同**的 `scopeTarget` 派发，而它是工作的 |
| 4 | 官方 answerer 先注册、veto 了整条 waterfall | 加了 `{ prepend: true }` 后依然毫无变化（而且那个参数压根没生效，见下） |

## 真正的原因

**我这个会话的 agent 根本没有 `ask_user_question` 工具。**

统计本会话全部工具调用分布，一次就清楚了：

```
run_code            1750
bash                   5
read                   1
plan                   0
ask_user_question      0
```

我一直在尝试「自己触发一次提问」来验证链路 —— 而我既没有 `ask_user_question`，
也没有 `plan`。**这条路上的第一个环节从来没发生过。**

而「电脑端出现了卡片」这个现象，让整件事看起来像是**链路中段坏了**；实际是那条路
**根本没被走到过**。我把「没被触发」误读成了「触发失败」。

## 该记住的

### 1. 排查前先确认「这个现象真的发生过吗」

我花在推理上的时间，远多于花在确认「数据里到底有没有这件事」上的时间。
最该做的第一个动作是查日志里有没有对应的 `tool/call` —— 一行统计，一分钟。

**判据：如果某个环节的日志一条都没有，那不是「执行失败」，是「压根没执行」。**
这两者的排查方向完全相反。

### 2. 编得出一个自洽的解释，不等于它是真的

上面四个「根因」每一个我都读了源码、引了行号、说得头头是道。
**自洽是最低标准，不是证据。**

区分方法：**这个解释有没有被实验证伪过？** 四个里只有第 4 个做了实验 —— 而它被证伪了，
我却没因此回头质疑前三个。

### 3. 一行实验 > 十轮推理

`{ prepend: true }` 是一行改动、一轮时间。我在做它之前先花了若干轮读 cordis 源码。
虽然那个参数最终证明无效（而且 `host.on` 签名只有两个参数，它压根没传进去），
但**它作为实验立刻排除了「注册顺序」这一整类假设**。

### 4. 让用户重复同一句话时，先想想为什么上一轮没成

用户发了三次同样的指令（「用 ask_user_question 问我一个问题」/「进入计划模式…」），
前两次都失败。**第二次失败时就该停下来查「我的工具集里到底有没有它」**，
而不是换个说法再让用户试一次。

## 同时记下的两个技术坑（这两个是真的）

### 坑 A：`callId` 只在 `wait` 里，而 `wait` 只有 `askTimed` 才加

`QuestionBridge` 最初的判据是「拿不到 `request.wait.callId` 就整条委托」。而：

- `dsh-user-questions/lib/types/index.js:252` —— **唯一的** `wait: { callId, timed: true }` 出现处
- `dsh-plan-mode/lib/index.js:259-262` —— plan 评审调 `ask({ questions, agent, signal })`，**没有 wait**
- `ask()` 自己（同文件 `:327`）只做 `{ ...request, agent }` 转发，**不会补 wait**

于是这条判据**把绝大多数提问挡在门外**：那种 request 直接 `return delegate` 交给官方界面 ——
**电脑端因此有卡片，而手机端一帧收不到**。两个现象，同一个原因。

改法：`callId` 缺失时**自造** `bridge-<uuid>`（本插件内部的关联键，不是内核的 ToolCallId）。
真正拿不到就没法工作的只剩两个：会话（定位用）与题目（空的无意义）。

> 通用教训：写「拿不到 X 就放弃」的判据前，先问一句 ——
> **拿不到 X 的时候，是该放弃，还是该自己造一个 / 降级处理？** 多数情况是后者。

### 坑 B：`pnpm build` 不查类型，`prepack` 才查

清理临时诊断代码时，`QuestionBridge` 构造器的第三个参数（诊断用的 `log`）删了，
但**调用处还传着**。`pnpm build`（tsdown）一路绿灯，是 `npm publish --dry-run` 触发的
`prepack → pnpm check → tsc --noEmit` 才抓到：

```
src/host/dsh-0.2-bridge.ts(773,8): error TS2554: Expected 2 arguments, but got 3.
```

**如果当时直接 publish，这次发布会失败。**

> 启示：`npm pack` / `npm publish` 的 `prepack` 钩子是发布前最后一道闸，
> 它跑的是完整 check（typecheck + test + docs:check + build），
> 比单独跑 `pnpm build` 严格得多。**发版前务必先 dry-run 一次。**

同一个参数上还挂着 `{ prepend: true }` —— 诊断期间加的，`host.on` 签名只有两个参数，
**它从来没生效过**。也就是说「注册顺序」那个假设，连被测试的机会都没有。已删除。

## 一句话

**先确认现象存在，再解释现象。** 前者一分钟，后者我花了一个下午。
