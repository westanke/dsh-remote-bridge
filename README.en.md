`dsh-remote-bridge` is the remote-access bridge plugin for DeepSeek Harness (DSH). It translates DSH's private remote protocol into **two device protocol surfaces**: the bidirectional `/ws/mobile` frames (every new capability lands only here, since v2.8) and the versioned REST `/api/v1` (legacy: frozen, shrink-only, being retired) so dsh-Chat ([GitHub](https://github.com/westanke/dsh-Chat) · [Gitee](https://gitee.com/westanke/dsh-Chat)), among other trusted clients, can keep using the same chat, workspace, and file capabilities while away from the machine. On the desktop it provides a **Phone settings** section inside your DSH settings, rendering collapsible cards inline: five in the main list (Remote / Public tunnel / Devices / Trash / App download) plus a collapsed-by-default **Advanced settings** group holding Roots, Image reading and Plugins — every card folds on its own and several may stay open at once.

**Who it is for**: people who use DSH as their main tool but do not want to be tied to the desk. Remote access is **off by default** — until you enable it, the plugin listens on loopback only, so installing it never exposes the machine to the LAN by itself.

The interface is bilingual and defaults to Chinese. Prebuilt packages run on Windows, macOS, and Linux without compiling on the target server.

> **Version warning**: the published `v2.0.0` and `v2.0.1` have serious defects (`v2.0.0` fails to read any historical images; `v2.0.1` cannot activate the plugin). Use **`v2.2.0`** (or ≥ `v2.0.4`).
> `v2.0.2` and `v2.0.3` were **never released** — do not look for installers under those version numbers.
>
> **DSH 0.2.x compatibility** and the **0.2.1-rc.2 adaptation notes** involve the trade-offs of the
> injected services and run long, so they live in
> [Compatibility & known limits](#compatibility--known-limits) — worth a skim before installing.

## About the rename (2.0.4)

The plugin was renamed from `dsh-workspace` to `dsh-remote-bridge`. The old name was narrower than the content: the plugin actually translates DSH's private remote protocol into versioned REST so a phone can reach this machine remotely, and adds a settings center on top — "workspace" is only one page of that.

**The rename only changes what you install and what the bundle is called. The following external contracts are deliberately unchanged:**

| Unchanged | Location | Why it must stay |
| --- | --- | --- |
| REST prefix `/dsh-workspace-api` | `src/host/server.ts` | Published apps hard-code it |
| State directory (`dataDir`, default `dsh-workspace`) | DSH profile config | A new directory would erase every authorized root and the trash |

**Two items that are no longer contracts** (both retired with the standalone page in 2.2.0):

- **The standalone page path `/dsh-workspace`**: that page (file tree + CodeMirror editor) was deleted, so the path went with it. It is a different thing from the REST prefix `/dsh-workspace-api` — **the prefix stays and remains the app's contract; the page is gone and promises nothing**.
- **The browser storage key `dsh-workspace-device-token`**: only that deleted page ever read or wrote it; nothing in this repo or in the app touches it now. A key nobody reads is not a contract, so it is not listed above. The name itself is not recycled, to avoid adding a red herring when debugging later.

So seeing `dsh-workspace` in a REST address or the state directory is **expected**, not an incomplete rename.

## Quick install

### Requirements

- A working DeepSeek Harness WebUI installation
- DSH kernel **`>=0.2.2-rc.1 <0.3.0`** (compatible with `0.2.2-rc.1` and every later `0.2.x`;
  schedule create/edit only exists on the kernel remote surface since `0.2.2`, and attachment
  reads rely on the 0.2.2 semantics — see
  [DSH 0.2.x compatibility notes](./docs/project/DSH-0.2-COMPAT.md) and the
  [DSH 0.2.2 adaptation survey](./docs/project/DSH-0.2.2-ADAPTATION.md)).
  `package.json` declares the same range under `engines.dsh`; the kernel resolves it with semver and
  only **disables** the plugin when unmet (the host process keeps running), with the user able to
  grant an exact-version exemption as the kernel suggests.
- Node.js `^22.19.0` or `>=24.0.0`
- Port `3090`, or another available port

Run as the same operating-system user that runs DSH WebUI. **The npm package name is recommended** — all three routes install the same build:

```sh
# 1. npm package name (recommended: a prebuilt tarball, so pnpm never asks to approve a build)
dsh plugin --profile web add dsh-remote-bridge

# ...or point at the mainland-China mirror
dsh plugin --profile web add dsh-remote-bridge --registry https://registry.npmmirror.com

# 2. tarball from the GitHub release
dsh plugin --profile web add https://github.com/westanke/dsh-remote-bridge/releases/download/v2.14.0/dsh-remote-bridge-v2.14.0.tgz

# 3. tarball from the Gitee release (faster from mainland China)
dsh plugin --profile web add https://gitee.com/westanke/dsh-remote-bridge/releases/download/v2.14.0/dsh-remote-bridge-v2.14.0.tgz

npx @deepseek-ai/dsh web
```

> `dsh plugin add` is a thin wrapper over `pnpm add`, so pnpm options such as `--registry` work directly.
>
> This README is shared verbatim by GitHub and Gitee, so any address that must carry a hostname
> (the install commands, release downloads) lists both hosts. Relative links follow the site you
> are reading on, but `/releases/download/...` has no relative form. The npm package name is the
> same as the GitHub repository, so it reads identically on both hosts.

Restart DSH after installation, then open settings — The section is titled **📱 Phone settings**. It is settings-only and does **not** contain the file tree. The in-conversation **Files** tab was removed in 2.0.4. **The desktop no longer offers a UI for browsing or editing files**: the standalone page `/dsh-workspace` was deleted in 2.2.0 — use the phone app, or ask the agent to use its tools in a conversation.

To install a downloaded release archive:

```sh
dsh plugin --profile web add ./dsh-remote-bridge-v2.14.0.tgz
```

## First connection

1. Open DSH settings and go to **Phone settings** (it lands on **Roots**).
2. Add a local directory under **Roots** and give it a recognizable label.
3. For mobile access, go to **Remote**, enter the bind IP and port, and save them.
4. Select **Enable and create pairing**, then enter the ten-minute one-time code in the app.
5. In the phone app's file page, select that root to browse and edit files.

Remote access cannot be enabled before at least one root exists. Installing the plugin does not expose it to the LAN; it listens on loopback until a local administrator enables remote access.

## Features

### No file-management UI on the desktop

2.2.0 deleted the standalone page `/dsh-workspace`, including the whole file tree, the upload/download entry points, and the CodeMirror 6 editor. The phone app's file page already covers the same ground natively, nobody used the desktop page, and it bloated the published package from **0.25 MB to 1.72 MB**.

The cost, stated plainly — **on the desktop there are now only two ways to touch files**:

1. Talk to the agent in a conversation and let it read and write files with its tools;
2. Open a terminal and do it yourself.

Mobile is unaffected: the app's file page still works against the same REST file endpoints the plugin kept (`/dsh-workspace-api` prefix, `/roots`, `/roots/{rootId}/content`, and so on — none were removed). Trash entries now come only from the phone app.

### Desktop settings panel

The entry lives in DSH settings under the title **Phone settings**. It renders seven cards stacked inline — no pop-up, no navigation rail — landing on **Roots** expanded:

| Section | Purpose |
| --- | --- |
| Roots | Add or remove authorized directories and set display labels. The current DSH workspace is registered automatically as a **default root** — it cannot be removed, but it stays fully accessible |
| Remote | Set bind IP/port, enable remote access, and create pairing codes |
| Devices | Inspect and revoke device scopes and per-root grants |
| Image reading | Set the handoff directory (the image-reading path); shows the read-only factory default `.dsh-images` and the fallback directory |
| Trash | View and restore deleted entries (only deletions made from the phone app appear here) |
| Plugins | See what this profile has installed, enable or disable it, check for updates, and jump to the kernel's plugin list |
| App download | Scan to install dsh-Chat; the codes point at both hosts' Releases list pages |

The sidebar gear button was **removed**: having the entry in both the sidebar and the settings page gave one thing two starting points. The in-conversation **Files** tab is gone too, so the desktop now has exactly one entry point.

### Image handoff: a picture sent from the phone, visible on the desktop

When the active model cannot see images (a text-only model), this plugin saves the picture as a workspace file **before the message is sent**, and the message keeps exactly two things: one plain-language line (where the file went, and what to do to view it) plus one absolute path for an image-reading tool.

**The DSH WebUI now renders that picture at the end of the turn** — click for the full image, `Escape` or click anywhere to close — while the path stays underneath it. The phone app could already show it; the desktop previously showed only text. Both now agree.

- **Where it lands**: `<session working directory>/<image path>/<sha256>.<ext>`. The file name is a content hash, so sending the same picture twice never piles up copies (directory `0700`, file `0600`).
- **Image path** defaults to `.dsh-images` and is editable under the **Image reading** section of the settings panel; changes take effect immediately, with no restart. The **Current default** field is **read-only** — past handoff messages and image-reading tools wrote their paths against it, so it does not follow your edit. The section also shows the fallback directory used when a session working directory cannot be resolved.
- **Only the handoff sentence is parsed**, and only in **your own message**: `.dsh-images/…` references inside assistant prose, context injections, or tool output are never turned into pictures (they are everywhere, and rendering them just shreds other people's words).

> If you previously installed `dsh-image-paths`, **disable** that row: both plugins attach their gallery to the same seat, so one picture would be drawn twice. This plugin already carries the capability.

### Clients and stable client API

Two client repositories are listed side by side; both talk to the same bridge:

- **[dsh-companion](https://github.com/westanke/dsh-companion) ([Gitee](https://gitee.com/westanke/dsh-companion))** — the Android client, a fork of the upstream [dsh-android-app](https://github.com/Hakunm/dsh-android-app). **No longer maintained or updated**; kept for historical reference only.
- **[dsh-Chat](https://github.com/westanke/dsh-Chat) ([Gitee](https://gitee.com/westanke/dsh-Chat))** — Flutter (`app/`, Android 1.0.36 released, with the iOS channel and the HarmonyOS Flutter-OH host) plus the frozen legacy HarmonyOS ArkTS build (`harmony/`). It targets bridge ≥ 2.10.0 (protocol v3, `dsh-mobile-v1` subprotocol).

**There is also an "Access" panel inside dsh-Go (v2.15.0 onwards)**. dsh-Go has a native plugin
protocol: a plugin declares entries in its `package.json` under `dshGo` and registers view functions
in the host process, and the app draws them itself. We use it for a **read-only** dashboard —
remote-access state, listening port, LAN access address, Cloudflare tunnel, root count, and the
authorized device list (name / platform / model / last seen) — plus a one-line strip above the
composer (`Remote on · 2` / `Local only`) that opens the panel when tapped. Its only action is
"copy access info".

**Read-only on purpose**: switching remote access, minting pairing codes and revoking devices are
write operations guarded in the WebUI by device tokens, scope bits and the tunnel runtime. A dsh-Go
connection is an ordinary kernel client and has **no mapping** to this plugin's device table, so a
write button there would let any dsh-Go client bypass the admin surface and change security state.
Opening that door needs a "dsh-Go connection → plugin device/permission" mapping first — a separate
decision (see [SECURITY.md](docs/project/SECURITY.md)).

Once the app is installed, generate a **connection code** or a pairing code under
**Phone settings → Remote access** to connect it to this machine.

The connection code is one line, `<url1>,<url2>,…#<pairingCode>`: the left half is an
**ordered candidate list** (tunnel first, then the LAN and virtual-network addresses detected on
this machine), the right half is an 8-character, 10-minute, single-use pairing code. A client that
probes picks the local address at home and the tunnel when you are away, so one line works in both
places; older clients that only read the first entry still get the tunnel, which works everywhere.
Add your own public address (DDNS + port forwarding, or IPv6) by passing it in `endpoints`.

Since 2.17.0 the long `DSH1:` text is no longer generated (issue #28): a 400+ character single-line
credential gets **characters dropped** when forwarded through WeChat or email, which turned the
device token into a key that matched no row in the database — the phone only reported "token is
invalid" with no hint that the message itself had been mangled.

The public API is independent of DSH private wire protocols. Authorized clients can:

- list, register, rename, and remove DSH workspace registrations;
- create, rename, fork, and archive sessions;
- read history, stream text and reasoning, steer messages, and cancel runs;
- display TODOs, slash commands, permission modes, and approval requests;
- select Agents, models, and reasoning effort;
- inspect or update built-in and fully custom model providers;
- manage files and trash within explicitly granted roots.

## Remote access and security

The default remote target is `0.0.0.0:3090`; both values are configurable. Clients may connect through any reachable IP address or domain name.

HTTP is supported and TLS is not mandatory. That keeps trusted-LAN and temporary deployments simple, but plain HTTP sends device tokens, chat, and file content in clear text. Use HTTPS through Caddy/Nginx, a VPN, Tailscale/WireGuard, or a trusted tunnel on public or untrusted networks.

The following controls remain active over both HTTP and HTTPS:

- ten-minute, single-use pairing codes;
- 256-bit device tokens stored server-side only as digests;
- revocable scopes and per-root grants;
- separate rate limits for pairing, authentication failures, and normal requests;
- audit records that omit tokens, file bodies, and chat bodies;
- no automatic access to roots added after a device was paired;
- provider `baseURL` changes are limited to public http(s) destinations, and moving a
  provider that already stores a credential to a new host also requires a fresh API key
  (the kernel sends that key to the address, so this is a credential boundary, not just SSRF).

Only a loopback client may add roots, change device grants, create pairing codes, configure the listener, or permanently purge trash.

### Local LLM endpoints (ollama / LM Studio)

Private, loopback, link-local and CGNAT provider addresses are **rejected by default**.
To use a local model server, list it explicitly in the plugin config:

```yaml
allowPrivateProviderHosts:
  - 127.0.0.1:11434     # recommended: pin the port
  - 192.168.1.5         # bare host: allows every port on that host
```

Exact `host` or `host:port` only — CIDR is not supported. Prefer the `host:port` form:
allowing `192.168.1.5` allows every service on it, while ollama only listens on 11434.
See `docs/project/SECURITY.md` for the reasoning and the audit trail fields.

## Path boundary

External requests use `rootId + relativePath`, never an absolute server path.

- Wire paths use `/`.
- Absolute paths, drive letters, UNC paths, backslashes, null bytes, and `.` or `..` segments are rejected.
- Every operation checks path segments for symlinks, junctions, and reparse points.
- Deleting a final link removes the link itself without traversing its target.
- Save temp files are placed beside the destination to avoid cross-device replacement failures.

Removing a DSH workspace removes only its WebUI registration. Directories, files, and session logs remain. Archiving a session hides it from the default list while preserving its log.

## Public API (two protocol surfaces)

**The primary surface is WebSocket frames** — every new capability lands only here:

```text
ws://HOST:PORT/ws/mobile
```

Handshake subprotocol `dsh-mobile-v1` (plus `dsh-pair.<code>` when pairing for the first time, then `dsh-auth.<token>` or `Authorization: Bearer`). Clients send `{type:…}`, the server replies `{kind:…}`, and `hello` arrives on connect with the capability bits. Frames and semantics: [API.md, mobile gateway](./docs/project/API.md#移动端网关-websocket-wsmobile). `dshrb-v1` opens the generic kernel-call surface.

### Why frames instead of REST

REST is request/response: the client must know a path for every operation, and the server can never speak first. Phones need the opposite —

- **Approvals, questions and streaming replies must wake the client.** Over REST you poll: slowly, or for nothing; a frame connection lets the server push.
- **Every capability used to cost a new path.** Path × method × error codes × docs, written again each time, and two parallel contracts drift. A frame costs one `type`, announced at runtime through the capability bits in `hello`.
- **Reconnects must resume.** History replays by `seq` and `connection-resync-required` says plainly that state must be rebuilt; REST clients had to invent that.
- **Large files should not be base64.** Frames chunk transfers (512 KiB down / 256 KiB up) with a sha256 check on the last chunk; REST upload is one base64 blob or a second upload session.

The cost is real: long connections need heartbeats and reaping, tunnels and reverse proxies must survive upgrades and idle timeouts, and the implementation is more complex. That is why REST has not disappeared: old clients still use it, and read surfaces with no frame equivalent (background jobs, pending approvals/questions, subagent history, attachment bytes) stay. See [API.md's protocol-surface table](./docs/project/API.md#协议面状态与弃用表2026-11-20-起).

**REST is legacy**: frozen, shrink-only. The per-endpoint deprecation table (replacement frame plus earliest removal in 3.0.0) is in [API.md's protocol-surface section](./docs/project/API.md). The table below remains for not-yet-updated clients and capabilities that have no frame equivalent. **Published clients are unaffected**: the 21 deprecated operations keep working until 3.0.0.

REST base URL:

```text
http://HOST:PORT/api/v1
```

Every request except health and pairing exchange uses:

```http
Authorization: Bearer DEVICE_TOKEN
```

## Device scopes

| Scope | Access |
| --- | --- |
| `chat.read` | Workspaces, sessions, messages, TODOs, commands, and approvals |
| `chat.write` | Manage workspaces/sessions, send, configure, run commands, and decide approvals |
| `files.read` | Browse, read, download, and view trash |
| `files.write` | Create, edit, upload, move, and rename |
| `files.delete` | Move files or directories to plugin trash |
| `settings.read` | Effective provider configuration and credential presence |
| `settings.write` | Provider changes, credential writes, and custom providers |

A device also needs an explicit grant for every `rootId`. Local administrators may change or revoke both scopes and root grants at any time.

**New scopes are picked before pairing, in Remote access**: whatever you tick is what the generated pairing code carries, and those scopes take effect once the app enters the code. For a device that is already paired, open **Devices** and use its **Permissions** button.

The default selection is five scopes — `chat.read`, `chat.write`, `files.read`, `files.write`, `settings.read` — and **deliberately excludes** `files.delete` and `settings.write`. You can still tick them; the default just no longer hands out destructive permissions on its own.

### Device names and models

At pairing time the bridge has no idea who will use the token, so a new device starts with a **platform-neutral** placeholder name (`Mobile device`). The first time the device connects, the bridge works out its platform and model from the request and replaces the name with `platform · model` (for example `HarmonyOS · <model>`).

Platform detection prefers the client-declared `X-Dsh-Device: <platform>/<model>` header and falls back to the `User-Agent`. **The model is only taken from what the client reports**: neither okhttp nor ArkWeb puts a model in its default UA, and the bridge will not guess — a wrong model is worse than no model.

Open **Devices** and use **Permissions** to rename a device. **A name you set yourself is never overwritten**; an automatically generated name still updates when the device reports a new identity. Device names are for display and troubleshooting only and take no part in authorization.

**Revoking a device deletes it from the database** rather than leaving a marker row behind. Its grants go with it, while the audit trail (who revoked which device, and when) is kept.

## Upgrade and uninstall

Stop DSH WebUI before upgrading, install the new package, then restart it. To uninstall:

```sh
dsh plugin --profile web remove dsh-remote-bridge
```

State is stored under `dsh-workspace` in the active `DSH_HOME`. Uninstalling does not erase state or trash, preventing accidental loss of recoverable files.

The 2.0.4 rename does not change that directory name: after upgrading, existing root grants and trash stay where they are. No migration is needed.

## Compatibility and known limits

### Some DSH builds have no attachment store

DSH's cordis injection properties (`ctx.attachments` / `ctx.fileUploads`) resolve lazily, and reading a service that nothing provides throws. Since 2.0.3 the plugin reads them tolerantly: when a service is absent the plugin still activates, and only the endpoint that actually needs it returns a readable error:

- `ATTACHMENT_STORE_UNAVAILABLE`: no `ctx.attachments`, so stored image bytes cannot be read.
- `FILE_UPLOADS_UNAVAILABLE`: no `ctx.fileUploads`, so attachments cannot be sent.

The user-visible consequence: **if this DSH build provides no attachment store, historical images in conversations cannot be displayed, but everything else in the plugin works normally** — and clients show the specific reason instead of a vague "image unavailable".

## Troubleshooting

**Phone settings is missing**

The entry is inside DSH settings, under the title **📱 Phone settings**. If you cannot see it, make sure the plugin was installed into the `web` profile and **restart DSH** — plugins load in-process and a restart is required.

**There is no UI for browsing or editing files on the desktop**

That is intentional in 2.2.0: the standalone page `/dsh-workspace` was deleted and the desktop no longer offers a file-management UI. Use the phone app's file page, or ask the agent to read and write files with its tools in a conversation.

**Enable and create pairing is disabled**

Add at least one root. If the bind IP or port changed, save the listener settings first.

**The phone cannot connect**

Confirm remote access is enabled, the firewall/security group allows the port, and the address is reachable from the phone. Do not use the server's own `127.0.0.1` address.

**A save reports a conflict**

Another window or process changed the file. Reload it, merge the desired changes, and save again.

**① Large uploads no longer blow up the host's memory (issue #23)**: uploading a 100 MiB file
to a phone pushed the bridge process (which *is* the host process) peak memory to **5.67×**
(100 MiB → 567 MiB) — no error, no dropped connection, no log line, just a quiet OOM.
Two "fully materialize" spots were the cause: `src/host/ws-file-transfer.ts`'s `uploadFinish`
does `readFile(spoolPath).toString('base64')` after the SHA-256 check, and
`src/host/bff-upload.ts`'s `complete` `readFile`s every chunk, `Buffer.concat`s them, and
`toString('base64')`s the whole thing — a structural floor of ≈4.67N (spool Buffer(N) +
base64(1.33N) + kernel decode(N) + a second base64(1.33N) for verification + a Uint8Array
copy(N)). The kernel already exposes a **streaming** entry point,
`ctx.fileUploads.uploadStream({ sessionId, data, signal?, name? })` (backed by
`attachments.saveFileStream` → chunk-by-chunk writes with bounded memory), but the bridge
always used base64. Both entry points now **try the stream first and fall back to base64 only
when streaming is unavailable**: measured peak over baseline for a 100 MiB upload drops from
**327.1 MiB → 2.5 MiB** (WebSocket) and **435.2 MiB → 46.6 MiB** (REST). The fallback is done by
**the layer that still holds the bytes** (the WS spool file and the REST chunk files can be
re-read); the kernel adapter receives a one-shot `AsyncIterable`, so it can only report the
stable code `FILE_UPLOAD_STREAM_UNSUPPORTED` rather than falling back itself. The streaming RPC
timeout is widened to 10 minutes (the 10 s default is too short for big files, but it must
**not** be infinite). The App needs no change: the `file-upload-completed` frame and its
`receiptId` / `attachmentId` / `bytes` are all unchanged.

**② The tunnel tool no longer vanishes silently (issue #22)**: asking the agent to "open a
tunnel" over IM produced a tool that was **not in the model's visible tool list at all**, with
a single warn line in the plugin log. The cause: `src/host/im-command.ts`'s `createTunnelTool`
put a boolean `required: true` on an **attribute node**, while the kernel's
`ToolsService.register` unconditionally calls `assertSupportedJsonSchema` — which accepts
only a small subset, and `required` may appear **only** on a `type:'object'` node, with the
top-level `required` being an **array of property-name strings**. Both rules were broken, so
registration threw, the plugin swallowed the failure into a warn, and the tool disappeared.
The attribute node no longer carries `required`, and the top level is now
`required: ['url','text','deviceName']` (all three returned fields stay mandatory) — back
inside the subset the kernel accepts.

## Project

- Version: `v2.17.5`
- **v2.9.0 makes teammates (sub-sessions) readable**: the phone's team panel could list members and
  sub-sessions but could not open a single one, because `sessions.list` filters out every row with
  `origin === 'subagent'` (the bridge's own `dsh-0.2-bridge.ts:2327`, with a comment explaining that
  exposing them "only yields rows that crash on tap"), so any sub-session id hitting `/messages` gets a
  hard 404. Even past that visibility check the kernel's `validateAddress()` demands the
  `{ kind:'subagent', parentSessionId, childSessionId, mode }` discriminated union instead of a plain
  session address. This release adds a **read-only narrow port guarded by membership**:
  `GET /api/v1/chat/sessions/{leadSessionId}/subagents/{subagentId}/messages`. Authorization takes two
  steps — (1) the Lead session must be visible to the device (reusing `requireSession`, not a single rule
  relaxed); (2) membership must be vouched for by a projection the kernel itself publishes
  (`subagentCatalog[].id` or `agentTeam.members[].id`). Only then is history read directly, deliberately
  **without** calling `requireSession(subagentId)` — removing the `origin` filter would put "crash on tap"
  rows back into the list, while loosening `requireSession` would backdoor every session; the narrow port
  has the cleanest boundary. Read-only (non-GET always 405), and `SUBAGENT_NOT_FOUND` deliberately does
  not distinguish "does not exist" from "not your teammate", otherwise id existence becomes a probe
  surface. New capability bit `subagent-history-v1` (it must be separate from `history-v1`, which always
  404s on sub-session ids and therefore cannot advertise this). The same release re-checked DSH
  0.2.1-rc.2 → rc.5: 18 of the 19 packages the bridge depends on are byte-identical, the only diff being
  a single KDoc comment.
- **v2.7.1 is a defect-fix release**: the kernel's `sessionController.resolveAgent()` returns an
  `{ agent }` / `{ error }` **envelope**, not the Agent itself (`dsh-api-session-controller/lib/index.js:365-368`
  `liveAgent()` and `:221-246` `resolve()` both have that shape). The bridge used to hand the envelope
  straight to `fileUploads.upload()`, so the kernel reading `agent.session.header.origin` blew up with
  `DSH_TYPEERROR: Cannot read properties of undefined (reading 'header')` — on a real device this showed up
  as "sending a file always fails with 400/500 and the message points nowhere", breaking both attachment
  upload and agent-preset selection. The bridge now detects the envelope, unwraps `.agent` on success, and
  rethrows `.error` as-is (keeping the kernel's stable code, so "session not found" is no longer flattened
  into "session not running"), while still accepting a bare object. Three regression tests pin all three
  return shapes.
- **v2.7.0 aligns with DSH 0.2.1-rc.3 and lifts four capabilities**: (1) the model catalog now carries
  `contextWindow` / `maxTokens` — the kernel's `ModelCatalogModel` only has id/name/description, so the
  bridge resolves capacity through `llm.resolveModelInfo`, caching per `provider + model` for ten
  minutes, never caching a failure, and never overwriting a value the kernel already supplied;
  (2) the plugin inventory gains a right-sidebar form (the bridge becomes a `SidebarRightTabDefinition`
  provider, so from DSH 0.2.1-rc.3 the card can be pinned; on rc.2 it still renders but has no pin or
  More menu, which is the expected degradation); (3) `POST /chat/sessions` accepts an optional
  `reuseBlank`, matching the 0.2.1 desktop behaviour where New Session returns to the workspace's
  existing blank session, skipping blanks whose preset contradicts the request; (4) the settings page
  gains a Plugins card (inventory / enable / disable / check for updates) and an "open plugin list"
  button (rc.2 has no `pluginNavigation.openList`, so the bridge feature-detects instead of checking
  versions).
- **v2.6.1 is the security-fix + device-identity release**: it closes a **high-severity** hole —
  the three provider `baseURL` entry points (create / update / model discovery) performed no
  validation at all, so a device holding `settings.write` could point the baseURL at its own server
  and the kernel would request `/models` there with **that provider's real API key**, leaking the
  credential outright; the persistent variant was worse, since after changing the baseURL every
  subsequent chat would send the key there. There are now three gates (protocol allow-list,
  private networks denied by default with an explicit `allowPrivateProviderHosts` opt-in, and a
  new key required when repointing a provider that already holds a credential), and the pairing
  default was narrowed from seven scopes to five (no more `settings.write` / `files.delete` by default).
  It also fixes "the device name is always 'Android device'": the bridge now derives the platform and
  model from the `X-Dsh-Device` header (User-Agent as fallback), renames the placeholder to
  "platform · model", and offers a rename channel (a manually set name is never overwritten).
- **v2.6.0 is the plugin-settings + IM-entry release**: it adds the per-plugin settings namespaces (`GET /api/v1/settings/namespaces`, `PATCH .../{ns}`) so the app can build the form from the kernel schema, and two entry points for "I am out and the desktop is still locked" — the host command `/tunnel` and the tool `open_tunnel_config`; plus one-tap pruning of unused devices, the audit page removed, and a guard so a failing optional registration cannot tear down the whole plugin context.
- **v2.5.2 is a comprehensive hardening release**: it lands the five-dimension audit
  (security, features, performance, UI, button feedback) — including the unauthenticated
  `debug/host-services` information disclosure fix, dual-bucket rate limiting, broadcast backpressure,
  weak ETags, and audit retention — and makes "start tunnel & generate token" complete inside a single
  request. While the tunnel runs, the management surface is safely locked with only "stop tunnel"
  available, restoring automatically afterwards. v2.5.1's security model (403 on `/manage` while a tunnel
  runs, the four-layer admin criteria) is unchanged; see `docs/project/SECURITY.md` §「管理面的信任边界」.
- **v2.5.1 was the security release**: it closed the remote privilege escalation and the `.heif`
